# Governance

DFPL uses specification-first governance.

A normative change proposal should identify:

1. affected kernel component(s) `G,T,N,IR,C,S,D`;
2. compatibility and migration impact;
3. whether Kernel identity changes;
4. required conformance vectors;
5. proof obligations;
6. reference implementation impact;
7. security implications;
8. documentation and release implications.

No implementation, runtime, package, agent, person, or external institution may silently redefine a sealed kernel version while continuing to claim conformance to the same Kernel ID.

Historical source material is informative archaeology unless explicitly promoted into the active normative specification.
